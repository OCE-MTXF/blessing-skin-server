# Offline plugins and removed high-trust web settings

The app starts with **no executable plugins**. A package on disk is not an approval. The runtime loads a plugin only if the installation is ready, the deployment identity approved the exact `(name, version, SHA-256 tree digest)`, and a separate activation flag selects that same tuple. Old name/version flags do not carry over. Approval is an authorization to run **trusted application code**, not a sandbox: PHP providers, bundled dependencies, bootstrap, translations, templates, and first-party-origin scripts must all be reviewed. An admin account cannot upload, download, extract, delete, or approve package code through the app. Core release changes follow the separate [offline deployment and upgrade procedure](deployment/README.md).

## Transition from an older release

1. Stop old Web workers, queues, and jobs. Back up and inventory the database, code, settings and plugin trees offline. Preserve legacy names and versions as inventory only; do not import legacy activation flags as approvals. If integrity is in doubt, obtain a known-good release via an authenticated publisher channel, review it and follow incident response instead of re-approving the old bytes.
2. Deploy to a clean release directory. Do not copy old `public/plugins/` or `public/lang/` into it. Remove old aliases and generated files from the serving path; block both URL prefixes at the edge and purge their cached responses as well as cached pages/bundles referencing them. Use only `public/` as document root. Do not alias private package trees, manifests, or `storage/` to any URL. Do not preserve outdated Vite dev markers or enable a production dev server.
3. Keep `PLUGINS_DIR`, `PLUGINS_APPROVALS_FILE`, and `PLUGINS_APPROVALS_SHA256` unset until review is complete. Upgrade the core independently and check readiness. Then approve and select only the packages you need, with prerequisites first. Retest essential application flows before unpausing traffic.
4. Configure the canonical HTTPS `APP_URL` and TLS/proxy policy as deployment settings. The old `site_url`, `force_ssl`, `auto_detect_asset_url`, `cdn_address`, `custom_css`, `custom_js`, `meta_extras` and reCAPTCHA settings are not used to emit URLs or code. After backups and review, remove the stale DB values through your offline maintenance process. Revoke legacy reCAPTCHA credentials at the provider, remove the retired secrets from active stores, and verify the local CAPTCHA flow. Do not paste old executable snippets into Markdown or weaken the CSP: review custom functionality and ship necessary CSS/JS as version-controlled, same-origin release assets or as part of an explicitly approved plugin.
5. Footer customization is Markdown (raw HTML is stripped). Convert each locale's old footer HTML to Markdown; `{site_name}`, `{site_url}`, and `{year}` are supported. Plain SEO title/description and palettes remain. Use local relative paths or full HTTPS URLs for the homepage image and favicon; unsupported URLs fall back to the built-in images. Frontend config and locale data are inert JSON in the page; translation changes never regenerate `/lang/*.js`.

## Prepare, pin and select a package

- In offline staging, verify the source and release provenance independently of the download location. Review `package.json`, the PHP, frontend assets and all bundled dependencies. Audit Composer-generated files too: path repositories, dependencies autoloaded by absolute path outside the package and code generators that modify the deployed tree are not supported. Bundled dependencies used at runtime belong to the reviewed tree. Never run development install scripts as the Web identity.
- Place one unpacked directory per package immediately under a dedicated private package root. `PLUGINS_DIR` accepts canonical absolute paths (comma-separated for multiple roots). Use a separate, non-admin application identity with read/list access only to the package tree and the approval file, and no edit, replace, rename, delete, owner/ACL-change, or equivalent rights on those entries or their ancestors. A read-only mount of deployment-owned files is preferable. Writing the parent directory can replace an otherwise read-only file. Do not store this content below `public/`, `storage/`, `bootstrap/cache` or any runtime-writable path; the app checks canonical paths and filesystem writability, but those checks do not replace correct ownership, ACLs, and mount isolation. In Windows deployments, check effective NTFS rights including delete-child, inheritance and directory reparse points; a file's read-only attribute alone is not sufficient. Use regular files only, with no links, junctions, or alternate streams. If the Web and deployment identities are the same or the Web identity can elevate, this trust boundary is not established.
- As the deployment identity, run the core release's `php artisan plugin:digest /absolute/path/to/reviewed-package` on the exact bytes to deploy. It prints a JSON record and does not execute the plugin or activate it. It covers the sorted relative paths and SHA-256 of regular file bytes (including `package.json`, scripts, templates and bundled vendors); checkout filters and line-ending changes change the digest. Package paths use portable ASCII segments, no case-folded duplicates, symlinks, hard links or non-regular files. Limits: 20,000 filesystem entries, 256 MiB total, 64 KiB manifest.
- Create a private UTF-8 manifest `{"schema":1,"packages":[…]}` using the exact records from `plugin:digest` (at most 128, one record per name). Set `PLUGINS_APPROVALS_FILE` to its canonical absolute path. Compute the lowercase SHA-256 of the entire file **as deployed**, and set `PLUGINS_APPROVALS_SHA256` explicitly from privately managed deployment config. File byte changes (including newline/encoding updates) require a new pin. Do not derive the pin dynamically from the file at application startup. Publish the tree and approvals together while traffic is paused; never edit package files in place while PHP can execute them. Clear any old route cache; route caching is not supported for runtime plugin routes. Update deployment-owned cached config if used, and restart PHP workers/OPcache. The app does not run plugin code in Artisan/queue processes.
- Use `php artisan plugin:enable <name>` (after installation readiness) or **Manage Plugins** as super-admin to select the approved digest. Settings changes never execute installation/deletion or enable/disable callbacks. Normal HTTP boot loads the approved package in dependency order. A wrong pin, modified tree, duplicate name, inactive dependency, version mismatch, cycle or conflict keeps affected packages disabled. Review mutually incompatible extensions offline. Plugin configuration is available to super-admin only after a package successfully loads; the installed list, approved README, and market catalog remain readable to administrators without activating anything.
- Use `php artisan plugin:disable <name>` or the super-admin UI to deactivate. Active dependants are also deactivated. For revocation, stop traffic/workers, remove the approval, replace the manifest pin and restart every serving worker. Remove superseded trees offline. Approval or version changes do not silently activate new bytes; explicitly reselect them. Do not rely on a disable toggle to undo already executed extension side effects or to retract previously downloaded assets.

## Compatibility and maintenance

- Migrate hard-coded `/plugins/...` URLs to `plugin_assets($name, $relativePath)` or `$plugin->assets($relativePath)`. Put assets in `assets/` of the approved package. The app serves them under `/plugin-assets/{name}/{digest}/{asset}` only for a currently loaded exact approval, with fixed content types, no sniffing and no caching. Supported file types are CSS, JS/MJS, PNG/JPEG/GIF/WebP and WOFF/WOFF2, up to 8 MiB per asset. HTML/SVG and executable-file suffixes are not served; inline scripts and remote CDN scripts are not supported. Use external same-origin JS files and event handlers compatible with the site's CSP. Do not put credentials or private data in assets.
- A deployment-owned `PLUGINS_CATALOG_FILE` is optional. It must be an absolute local JSON file; no remote fetch. Its `packages` list may contain up to 400 entries within 1 MiB. Fields shown are `name`, `version`, `title`, `description`, `author` and `require` (map of names to version constraints). The market is informational only: it does not accept distributions, execute code, approve digests, or contain install buttons. Without a file, the local list is empty.
- **Resource options** retains avatar/preview caching toggles. “Invalidate rendered texture cache” is an authenticated admin POST with a CSRF token. It rotates only the rendition generation; unrelated session, limiter and application caches are untouched. Old renditions expire normally. The old `clear-cache` GET parameter has no effect. On multiple nodes, use the same correctly namespaced application cache so every node sees the new generation.
